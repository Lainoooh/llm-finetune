## 1. 系统定位

`llm-finetune` 目标不是一个通用 SSH 运维平台，而是一个面向垂域模型训练的可视化微调工作台。系统围绕 LLaMA-Factory 的训练流程，将服务器资源、GPU 卡位、数据集、训练参数、训练日志、评测结果和多子任务对比组织成一套可操作的产品界面。

核心用户路径：

```text
配置服务器资源
  -> 探测 GPU / CUDA / PyTorch / LLaMA-Factory / 磁盘 / 工作目录
  -> 按 GPU 切分为可调度的服务器对象
  -> 创建微调任务
  -> 为任务创建多个子任务
  -> 每个子任务绑定一个服务器对象和一套训练参数
  -> 启动训练、查看日志和远程目录
  -> 执行评测
  -> 对比多个子任务结果
```

## 2. 当前代码所表达的产品雏形

当前根目录前端是 React + Vite 单页应用：

| 文件 | 当前能力 |
|---|---|
| `src/App.jsx` | 页面状态路由、全局 `servers` 和 `task` 本地状态 |
| `src/pages/Dashboard.jsx` | 服务器数量、子任务状态、Loss 趋势总览 |
| `src/pages/ServersPage.jsx` | 服务器列表、连接配置、环境信息、连通性检查 mock |
| `src/pages/TaskListPage.jsx` | 微调任务列表、搜索、状态筛选、任务编辑 mock |
| `src/pages/TaskDetailPage.jsx` | 单个微调任务下的子任务列表、并行启动、复制、删除 |
| `src/pages/SubtaskPage.jsx` | 子任务配置，包含基础配置、数据集、训练参数、远程目录、日志、评测 |
| `src/pages/ComparePage.jsx` | 子任务 Loss 与评测结果对比、报告导出 mock |
| `src/data/mockData.js` | 当前所有页面数据源 |

这说明前端已经不是单一“服务器管理”页面，而是一套训练任务工作流 UI。后端和远程执行插件应服务这个工作流。

```text
┌─────────────────────────────────────────────┐

│ 服务器管理 / 任务列表 / 子任务配置 / 对比      │
└─────────────────────┬───────────────────────┘
                      │ HTTP / SSE / WebSocket
┌─────────────────────▼───────────────────────┐
│ 应用后端 API                                 │
│ Server API / Task API / Subtask API / Run API│
│ 权限、状态机、资源锁、日志订阅、结果解析       │
└─────────────────────┬───────────────────────┘
                      │ 统一执行器接口
┌─────────────────────▼───────────────────────┐
│ Remote Execution Adapter                     │
│ Jupyter Terminal 临时插件                    │
│ 后续 SSH / Docker / K8s 执行器               │

                      │ 命令、文件、日志
┌─────────────────────▼───────────────────────┐

│ GPU / CUDA / PyTorch / 数据集 / 输出目录      │
└─────────────────────────────────────────────┘
```

## 4. 分层职责

### 4.1 前端层

职责：

- 展示服务器资源池和 GPU 卡位。
- 配置微调任务、子任务和训练参数。
- 发起训练、停止、重试、评测、刷新目录、下载日志等操作。
- 展示任务状态、实时日志、Loss 曲线、评测指标和对比结果。

不应该承担：

- 保存 Jupyter token。
- 直接连接远程 WebSocket terminal。
- 在浏览器内拼接高权限 shell 命令。
- 决定 GPU 锁是否可抢占。

### 4.2 应用后端层

职责：

- 提供稳定业务 API。
- 持久化服务器、GPU、任务、子任务、训练运行记录。
- 管理资源锁，避免同一 GPU 被多个子任务同时占用。
- 调用远程执行插件。
- 将远程命令输出解析成业务字段。
- 将长任务状态推送给前端。

### 4.3 远程执行插件层

职责：

- 把业务命令组发送到远程 LLaMA-Factory 容器。
- 维护远程会话、队列、超时和输出边界。
- 处理 Jupyter 通道异常并自动重建会话。
- 将 stdout/stderr 返回给后端。

定位：

- 当前阶段是临时通道，因为无法直连服务器。
- 插件接口要抽象，后续可以替换成 SSH、Docker API 或 Kubernetes Job。

### 4.4 训练运行环境

当前目标运行环境：

- LLaMA-Factory 容器镜像。
- 容器内可用 GPU。
- 容器内有 Python、PyTorch、CUDA、LLaMA-Factory。
- 工作目录可写，可存放数据集、配置、日志、输出模型。

后续目标：

- 系统可协助部署标准 LLaMA-Factory 微调镜像。
- 支持镜像版本管理和环境一致性校验。
- 支持宿主机到容器的目录映射规范。

## 5. 关键设计原则

### 5.1 任务与子任务分离

微调任务是业务目标，例如 `customer_service_v1`。子任务是实际执行单元，例如不同学习率、LoRA rank、epoch 或数据集版本的一次训练运行。

系统所有调度、GPU 占用、日志、输出目录和评测记录都应落在子任务上。

### 5.2 服务器对象是可调度资源，不一定等于物理机器

一个物理服务器可能有 8 张 GPU。为了避免冲突，可以拆成 8 个服务器对象：

```text
物理机 A: GPU 0,1,2,3,4,5,6,7
  -> 服务器对象 A-GPU0: gpuIds=0
  -> 服务器对象 A-GPU1: gpuIds=1
  -> ...
```

后续子任务绑定服务器对象，而不是直接绑定物理机。这样调度边界更清晰。

### 5.3 远程执行能力只作为基础设施

Jupyter 插件不能成为业务模型的一部分。业务层只认识：

- 探测服务器环境
- 创建工作目录
- 上传/同步配置
- 启动训练
- 停止训练
- 读取日志
- 读取评测结果

至于这些动作通过 Jupyter、SSH、Docker 还是 Kubernetes 实现，由执行器适配层决定。

## 6. 推荐技术栈

当前前端保持：

- React 18
- Vite
- 现有 CSS-in-JS 风格

新增后端建议：

- Node.js 原生 HTTP 或 Fastify
- SQLite 作为初期轻量持久化
- 后续可迁移 PostgreSQL
- SSE 或 WebSocket 做训练日志推送

原因：

- 项目当前就是 Node/Vite 生态，新增 Node 后端最顺滑。
- Jupyter Terminal WebSocket 客户端用 Node 原生 `WebSocket` 即可。
- SQLite 足够覆盖单机原型和本地部署。
