# 远程执行框架与连接方式扩展设计

## 1. 背景

当前平台需要通过远程服务器执行探测、脚本下发、训练启动、日志读取、评测等操作。现阶段可用连接方式包括：

- `jupyter`：通过 Jupyter Terminal WebSocket 操作远程 shell。
- `ssh`：通过 SSH 连接远程 shell。

这两种连接方式的底层建连方式不同，但业务上都应该表现为“向某台服务器发送一段 shell 脚本，并拿回结构化执行结果”。因此架构上不能让 Jupyter 和 SSH 各自重复实现队列、超时、marker、断线重连等执行框架能力。

## 2. 设计目标

- 前端只关心统一 JSON 请求和响应，不关心服务器使用 Jupyter 还是 SSH。
- 业务服务层只调用统一执行器，不直接操作 Jupyter WebSocket 或 SSH channel。
- 队列锁、超时、marker、输出归一化、断线重连、执行结果解析全部放在通用执行框架层。
- Jupyter/SSH 只实现“如何连接、如何写入 stdin、如何读取 stdout/stderr、如何关闭连接”。
- 后续新增 Docker API、K8s、Slurm、裸机 Agent 时，只新增 Transport，不重写执行框架。

## 3. 分层架构

```text
Frontend / API
  - 发送统一 JSON 请求
  - 接收统一 JSON 响应

Business Services
  - server probe
  - script run
  - subtask start / stop / sync / logs

RemoteExecutorFactory
  - 根据 ServerProfile.access_type 选择执行入口

QueuedRemoteSession
  - 长连接生命周期
  - 队列锁
  - 超时
  - marker 包装和结束判断
  - stdout/stderr 归一化
  - 失败 reset 和断线重连

RemoteTransport
  - JupyterTransport
  - SshTransport
  - Future: DockerTransport / K8sTransport / SlurmTransport
```

## 4. 核心接口

### 4.1 Transport 协议

Transport 只负责 IO，不负责脚本包装、marker、队列和业务状态。

```python
class RemoteTransport:
    @property
    def key(self) -> str: ...
    async def connect(self) -> None: ...
    async def send(self, payload: str) -> None: ...
    async def recv(self) -> RemoteFrame: ...
    async def close(self) -> None: ...
```

统一输出帧：

```python
RemoteFrame(kind="stdout" | "stderr", content="...")
```

### 4.2 通用会话

`QueuedRemoteSession` 持有一个 Transport，并统一实现：

- `asyncio.Lock` 串行队列。
- `ensure_connected()`。
- shell 初始化。
- base64 脚本包装。
- 唯一 marker 生成。
- `marker:exit_code` 解析。
- 超时后关闭 Transport。
- Transport 异常后关闭连接，下一次请求自动重连。

通用执行流程：

```text
run_script(script)
  acquire lock
  ensure_connected
  marker = make_marker()
  payload = wrap_script(script, marker)
  transport.send(payload)
  loop transport.recv()
    collect stdout/stderr
    if marker found:
      return RemoteExecutionResult
  timeout:
    reset transport
    raise timeout
```

## 5. JupyterTransport

Jupyter 只实现连接适配：

- `connect()`：
  - `POST /api/terminals` 创建 terminal。
  - 建立 `/terminals/websocket/{name}` WebSocket。
- `send(payload)`：
  - 发送 `["stdin", payload]`。
- `recv()`：
  - 读取 WebSocket frame。
  - 将 `["stdout", "..."]` / `["stderr", "..."]` 转为 `RemoteFrame`。
- `close()`：
  - 关闭 WebSocket。
  - 尝试删除 terminal。

## 6. SshTransport

SSH 只实现连接适配：

- `connect()`：
  - 使用 `asyncssh.connect()` 建立连接。
  - 创建长期 shell process。
- `send(payload)`：
  - 写入 shell stdin。
- `recv()`：
  - 从 stdout/stderr 读取内容并转为 `RemoteFrame`。
- `close()`：
  - 关闭 shell process 和 SSH connection。

SSH 不单独实现队列、marker、超时和重连，这些统一由 `QueuedRemoteSession` 处理。

## 7. 工厂设计

业务层调用统一入口：

```python
executor = get_executor_for_server(server)
result = await executor.run_script(script, timeout_ms)
```

工厂内部：

```python
if server.access_type == "jupyter":
    transport = JupyterTransport(...)
elif server.access_type == "ssh":
    transport = SshTransport(...)
session = QueuedRemoteSession(transport)
```

会话缓存 key：

- Jupyter：`jupyter:{base_url}`
- SSH：`ssh:{user}@{host}:{port}`

同一个 key 共享一个队列；不同 key 队列互相独立。

## 8. 数据模型扩展

`ServerProfile` 使用 `access_type` 表示连接方式：

```text
access_type = jupyter | ssh
```

新增 SSH 字段：

- `ssh_port`
- `ssh_key`

保留字段：

- `host`
- `user`
- `password`
- `jupyter_base_url`
- `jupyter_token`
- `work_dir`
- `gpu_ids`
- `finetune_tool_name`

API 使用 camelCase：

- `accessType`
- `sshPort`
- `sshKey`
- `jupyterBaseUrl`
- `token`

内部数据库 `id` 仍为雪花 long，不暴露给前端。

## 9. 前端交互设计

新增/编辑服务器弹窗中，在“微调工具”同一行左侧增加“连接方式”：

```text
连接方式： [ Jupyter ] [ SSH ]      微调工具： [ LLaMA-Factory ]
```

表单规则：

- `Jupyter`：
  - Jupyter Base URL
  - Token
  - 工作目录
  - 设备编号
- `SSH`：
  - Host
  - SSH Port
  - Username
  - Password
  - Private Key
  - 工作目录
  - 设备编号

连通性测试按钮仍调用：

- `POST /api/servers/probe-draft`
- `POST /api/servers/{server_code}/probe`

后端根据 `accessType` 自动选择 Transport。

## 10. 编码复杂度评估

| 模块 | 复杂度 | 说明 |
| --- | --- | --- |
| 抽通用执行框架 | 中 | 需要从现有 Jupyter 会话中拆出队列、marker、timeout、reset。 |
| Jupyter 改 Transport | 低到中 | 现有 WebSocket 逻辑可复用。 |
| SSH Transport | 中 | 需要 `asyncssh`，并处理长期 shell stdout/stderr。 |
| 后端 schema/model | 低 | 增加 accessType、sshPort、sshKey 字段。 |
| 前端表单 | 低 | 增加连接方式分段控件和动态字段。 |
| 测试 | 中 | 需要 fake transport 验证通用框架能力。 |

## 11. 测试策略

- FakeTransport 测试：
  - marker 能正确结束。
  - 非 0 exit code 能正确返回。
  - 超时会关闭 transport。
  - 多次执行按队列串行。
- JupyterTransport 冒烟：
  - 真实 Jupyter token 可执行 `df -h`。
- SSHTransport：
  - 单元层只测试参数构造。
  - 真实 SSH 连接作为可选集成测试。
- API 测试：
  - `accessType=jupyter` 创建/更新/探测。
  - `accessType=ssh` 创建/更新。
  - 响应不暴露内部 long `id`。

## 12. 约束

- 不拆分成 `/api/jupyter/...` 和 `/api/ssh/...`。
- 不允许前端根据连接方式调用不同业务接口。
- 不允许在 JupyterTransport 和 SshTransport 中重复实现队列、marker、超时。
- 训练启动等长任务仍通过统一执行框架投递远程脚本，执行记录使用 `run_code` 对外展示。

## 13. 服务器弹窗与显卡命名修订

服务器新增/编辑弹窗按“基础配置 + 连接方式 + 连接参数 + 环境信息”组织：

- 基础配置为连接方式无关字段：服务器名称、设备编号、工作目录。
- 连接方式与微调工具保持同一行：`Jupyter` / `SSH`，`LLaMA-Factory`。
- `Jupyter` 连接只展示：`Jupyter Base URL`、`Jupyter Token`。
- `SSH` 连接展示：连接账号、连接地址、连接密码，并保留 SSH Port、SSH Private Key 作为高级连接参数。
- 环境信息使用一行 3 个指标展示，字段为：显卡型号、CUDA 版本、显卡数量/编号、PyTorch 版本、微调工具版本、磁盘、状态。

前端展示层不再使用 `GPU/CUDA/PyTorch` 作为唯一口径，后端响应新增通用字段：

| 通用字段 | 兼容旧字段 | 含义 |
| --- | --- | --- |
| `accelerator` | `gpu` | 显卡型号摘要 |
| `acceleratorIds` | `gpuIds` | 当前服务器对象可用显卡编号 |
| `acceleratorCount` | - | 当前服务器对象包含的显卡数量 |
| `acceleratorVendor` | - | 设备厂商，例如 `nvidia`、`huawei`、`alibaba`、`unknown` |
| `acceleratorRuntime` | `cuda` | 运行时，例如 CUDA、CANN、PPU Runtime |
| `aiFramework` | `torch` | PyTorch 版本 |

后端脚本仍兼容当前 NVIDIA 环境，但探测脚本输出已预留统一契约：

```json
{
  "accelerator_vendor": "nvidia",
  "accelerator_runtime": "CUDA 12.1",
  "accelerator_driver": "driver version",
  "accelerators_csv": "index,name,uuid,memory.total,memory.used",
  "accelerator_ids": "0,1",
  "accelerator_count": 2
}
```

后续适配华为 Ascend、阿里 PPU 或其他设备时，只需要在 `server.probe_env` 脚本的 `detect_accelerators()` 中增加厂商探测命令，并保持 `accelerators_csv` 的五列契约；业务接口、前端页面和执行队列层不需要改动。

## 14. 探测任务拆分

`连通性测试` 按钮实际创建一个整体探测任务，任务下有两个互不冲突的子结果：

- `hardware`：宿主机执行，创建工作目录，探测显卡、驱动、磁盘和目录权限。
- `finetuneEnv`：宿主机先按用户填写的微调工具容器名查找 Docker 容器，找到后进入容器探测 Python、PyTorch、Transformers 和微调工具版本。

接口形态：

```text
POST /api/servers/probe-draft
POST /api/servers/{server_id}/probe
GET  /api/servers/probes/{probe_code}
```

前端点击后按钮保持 `探测中`，直到两个子结果都进入 `succeeded` 或 `failed` 才恢复。页面按子结果独立渲染：硬件先成功就先展示硬件信息；如果容器不存在，只在微调环境和微调工具版本处显示红色错误，例如 `没有找到 xx 容器`。
