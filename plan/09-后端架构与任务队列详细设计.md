# 后端架构与任务队列详细设计

> 状态：[草案]  
> 创建时间：2026-05-21  
> 最后更新：2026-05-21

## 1. 技术选型结论

建议后端使用 **Python FastAPI**。

原因：

1. 微调平台天然靠近 Python/ML 生态，后续解析 LLaMA-Factory 配置、训练日志、评测结果、YAML、数据集文件更顺手。
2. FastAPI + Pydantic 适合定义清晰 API schema，小型智能体实现时边界明确。
3. Jupyter REST/WebSocket 可以用 `httpx` + `websockets` 实现，不依赖浏览器。
4. 后续接入 Celery/RQ/Arq 或迁移 PostgreSQL 都比较自然。
5. 当前前端是 React/Vite，前后端完全可以通过 `/api` 解耦，不要求后端也用 Node。

推荐初期技术栈：

| 层 | 选型 | 说明 |
|---|---|---|
| Web API | FastAPI | REST API、SSE 日志流 |
| 数据校验 | Pydantic v2 | 请求、响应、配置 schema |
| 数据库 | SQLite + SQLAlchemy 2 | 原型阶段轻量，后续可迁移 PostgreSQL |
| 后台循环 | asyncio task | 初期实现队列、日志采集和状态轮询 |
| 远程执行 | httpx + websockets | Jupyter REST + Terminal WebSocket |
| YAML | ruamel.yaml 或 PyYAML | 保留 YAML 字段和格式 |
| 日志 | structlog/logging | 操作审计和任务日志 |

不建议当前引入过重依赖：

- Celery + Redis：后续多实例部署时再引入。
- Kubernetes：当前只是容器内微调执行，先抽象执行器接口即可。
- 前端直连 Jupyter：会暴露 token，且无法统一队列与审计。

## 3. 后端分层职责

```text
api/routes
  只做参数接收、权限校验、调用 service、返回响应

services
  业务规则：资源锁、状态流转、脚本选择、数据持久化

executors
  远程执行适配：Jupyter/SSH/Docker/K8s

workers
  后台任务：队列消费、日志采集、训练状态轮询、超时处理

models/schemas
  数据库模型和 API schema
```

## 3.1 存储 ID 约定

后端所有数据库表的 `id` 字段统一为雪花算法生成的 `BIGINT` / Python `int` / 前端 JSON number。该 `id` 是内部存储 ID，不作为页面展示编号。

展示编号单独存储：

| 对象 | 内部字段 | 展示字段 |
|---|---|---|
| FineTuneTask | id BIGINT | task_code |
| FineTuneSubtask | id BIGINT | subtask_code |
| ExecutionRun | id BIGINT | run_code，可选 |

数据库关联一律使用内部 `id`，例如 `subtasks.task_id` 指向 `tasks.id`。前端页面中显示的 `ID=bt001`、`task_002` 不再作为外键使用。

## 4. 两层队列设计

系统里必须区分两种队列，它们解决的问题不同。

### 4.1 业务任务队列：持久化队列

业务任务队列记录在数据库中，对应 `ExecutionRun`。它是“系统要做什么”的事实来源。

适用对象：

- 服务器探测
- 工作目录检查
- 配置同步
- 训练启动
- 训练停止
- 日志读取任务
- 评测启动
- 评测状态检查

特点：

- 持久化，可查。
- 服务重启后可恢复或标记为异常。
- 有明确业务状态。
- 与 UI 状态绑定。

表：`execution_runs`

| 字段 | 说明 |
|---|---|
| id | BIGINT，内部存储 ID，雪花算法生成 |
| run_type | `server_probe` / `train_start` / `train_stop` / `log_collect` / `eval_start` |
| target_type | `server` / `subtask` / `task` |
| target_id | 目标内部存储 ID |
| server_profile_id | 使用的服务器对象 |
| status | `queued` / `running` / `succeeded` / `failed` / `timeout` / `cancelled` |
| script_key | 使用的脚本模板 |
| script_version | 脚本版本 |
| rendered_script | 实际渲染后的脚本，便于审计 |
| timeout_ms | 超时 |
| exit_code | 退出码 |
| error_message | 错误 |
| created_at | 创建时间 |
| started_at | 开始时间 |
| finished_at | 结束时间 |

### 4.2 远程会话队列：内存短命令 FIFO

远程会话队列存在于 `JupyterSessionManager` 内部，对应一个 Jupyter terminal WebSocket。

它是“如何把命令送到远程容器”的传输队列。

特点：

- 每个远程访问端点一个队列。
- FIFO 串行发送命令。
- 每条命令有唯一结束标记。
- 会话断开后当前命令和队列失败。
- 不持久化，不跨 session generation 迁移。

```text
JupyterSessionManager(endpoint=47.94.137.97:30009/jupyter)
  generation=3
  terminal_name=1
  websocket=connected
  queue:
    remote_command_101 running
    remote_command_102 queued
    remote_command_103 queued
```

表：`remote_commands`

| 字段 | 说明 |
|---|---|
| id | BIGINT，内部存储 ID，雪花算法生成 |
| execution_run_id | 对应业务执行记录 |
| endpoint_key | Jupyter endpoint 标识 |
| session_generation | 会话代号 |
| status | `queued` / `running` / `succeeded` / `failed` / `session_reset` |
| marker | 唯一结束标记 |
| stdin_payload | 实际发送内容 |
| stdout | 输出 |
| stderr | 错误输出 |
| exit_code | 退出码 |
| error_message | 错误 |

### 4.3 为什么训练不应长期占用远程会话队列

如果直接在 WebSocket 中执行：

```bash
llamafactory-cli train train.yaml
```

这个命令会持续数小时，导致：

- 队列无法执行其他命令。
- 无法刷新目录。
- 无法停止训练。
- WebSocket 断开时难以判断训练是否仍在跑。

正确方式：

1. 队列只执行“启动训练后台进程”的短命令。
2. 训练进程在远程容器后台运行。
3. 训练日志写入远程文件。
4. 后端通过短命令定期读取日志增量和状态文件。

```text
队列命令 A: 写入 run.sh
队列命令 B: nohup bash run.sh > logs/stdout.log 2>&1 & echo $! > run.pid
队列命令 C: tail 增量读取 logs/stdout.log
队列命令 D: 检查 run.pid 和 status.json
```

## 5. 训练任务如何执行和读取

### 5.1 启动训练的后台脚本

每个子任务远程目录：

```text
subtask_dir/
  train.yaml
  dataset_info.json
  run.sh
  run.pid
  status.json
  logs/
    stdout.log
    train.log
  outputs/
  eval/
```

`run.sh` 示例：

```bash
#!/usr/bin/env bash
set -euo pipefail

cd "__SUBTASK_DIR__"
mkdir -p logs outputs eval

write_status() {
  python3 - "$1" "$2" <<'PY'
import json, sys, time
status, code = sys.argv[1], sys.argv[2]
payload = {
  "status": status,
  "exit_code": None if code == "" else int(code),
  "updated_at": time.time()
}
open("status.json", "w").write(json.dumps(payload, ensure_ascii=False))
PY
}

write_status running ""

export CUDA_VISIBLE_DEVICES="__GPU_IDS__"
set +e
llamafactory-cli train train.yaml 2>&1 | tee logs/train.log
code=${PIPESTATUS[0]}
set -e

if [ "$code" -eq 0 ]; then
  write_status succeeded "$code"
else
  write_status failed "$code"
fi

exit "$code"
```

启动命令：

```bash
cd "__SUBTASK_DIR__"
nohup bash run.sh >> logs/stdout.log 2>&1 &
echo $! > run.pid
```

这样训练进程和 Jupyter WebSocket 生命周期解耦。

### 5.2 如何读取训练状态

状态读取命令：

```bash
cd "__SUBTASK_DIR__"
python3 - <<'PY'
import json, os

def pid_alive(pid):
    try:
        os.kill(pid, 0)
        return True
    except Exception:
        return False

payload = {
    "pid": None,
    "pid_alive": False,
    "status_file": None,
    "status": "unknown",
    "exit_code": None,
}

if os.path.exists("run.pid"):
    pid = int(open("run.pid").read().strip())
    payload["pid"] = pid
    payload["pid_alive"] = pid_alive(pid)

if os.path.exists("status.json"):
    data = json.load(open("status.json"))
    payload["status_file"] = data
    payload["status"] = data.get("status", "unknown")
    payload["exit_code"] = data.get("exit_code")
elif payload["pid_alive"]:
    payload["status"] = "running"

print(json.dumps(payload, ensure_ascii=False))
PY
```

后端 `status_poller` 每 3-10 秒执行一次，更新 `ExecutionRun` 和 `FineTuneSubtask` 状态。

## 6. 实时日志读取设计

### 6.1 日志采集策略

后端维护每个 run 的日志偏移量：

表：`execution_log_offsets`

| 字段 | 说明 |
|---|---|
| run_id | 执行记录 |
| file_path | 远程日志文件 |
| byte_offset | 已读取字节位置 |
| updated_at | 更新时间 |

读取增量命令：

```bash
python3 - "__LOG_FILE__" "__OFFSET__" <<'PY'
import base64, json, os, sys
path = sys.argv[1]
offset = int(sys.argv[2])
result = {"offset": offset, "next_offset": offset, "content_b64": "", "exists": os.path.exists(path)}
if result["exists"]:
    size = os.path.getsize(path)
    if offset > size:
        offset = 0
    with open(path, "rb") as f:
        f.seek(offset)
        data = f.read(256 * 1024)
        result["offset"] = offset
        result["next_offset"] = offset + len(data)
        result["content_b64"] = base64.b64encode(data).decode()
print(json.dumps(result, ensure_ascii=False))
PY
```

后端解码后写入 `execution_logs`。

### 6.2 前端实时查看

使用 SSE：

```text
GET /api/runs/:runId/logs/stream
```

事件：

```text
event: log
data: {"seq":102,"stream":"stdout","content":"step=10 loss=2.114\n"}

event: metric
data: {"step":10,"loss":2.114,"lr":0.0000041}

event: status
data: {"status":"running"}
```

优点：

- 浏览器只连接后端，不连接 Jupyter。
- 后端可以补发历史日志。
- 前端刷新后可根据 `lastSeq` 续读。

### 6.3 Loss 指标解析

后端从日志内容中解析：

```text
step=10 loss=2.114 lr=4.1e-06 grad_norm=0.82
```

或解析 LLaMA-Factory 标准日志格式，写入：

表：`training_metrics`

| 字段 | 说明 |
|---|---|
| run_id | 执行记录 |
| subtask_id | 子任务 |
| step | step |
| epoch | epoch |
| loss | loss |
| learning_rate | lr |
| grad_norm | grad_norm |
| raw_line | 原始日志行 |

## 7. 后台 worker 设计

### 7.1 scheduler

职责：

- 扫描 `execution_runs.status=queued`。
- 根据资源锁和服务器状态决定是否执行。
- 调用对应 service。

### 7.2 log_collector

职责：

- 扫描 running 的 train/eval run。
- 根据日志偏移读取远程日志增量。
- 写入 `execution_logs`。
- 解析 metrics。

### 7.3 status_poller

职责：

- 扫描 running 的 train/eval run。
- 读取远程 `status.json` 和 `run.pid`。
- 更新 run/subtask 状态。
- 释放 GPU 锁。

### 7.4 cleanup_worker

职责：

- 清理超时的 remote command。
- 标记长期无心跳的 run。
- 清理过期临时 terminal。

## 10. 关键状态流

### 10.1 服务器探测

```text
POST /api/servers/:id/probe
  -> create ExecutionRun(server_probe)
  -> render script server.probe_env
  -> RemoteExecutor.run short command
  -> parse JSON
  -> update RuntimeEnvironmentSnapshot
  -> update ServerProfile
  -> return snapshot
```

### 10.2 启动训练

```text
POST /api/subtasks/:id/start
  -> validate subtask config
  -> acquire ResourceLock
  -> create ExecutionRun(train)
  -> render sync scripts
  -> write train.yaml / dataset_info.json / run.sh
  -> execute start_background command
  -> mark subtask running
  -> log_collector/status_poller take over
```

### 10.3 停止训练

```text
POST /api/subtasks/:id/stop
  -> read run.pid
  -> kill pid gracefully
  -> poll process
  -> force kill if needed
  -> mark stopped
  -> release ResourceLock
```
